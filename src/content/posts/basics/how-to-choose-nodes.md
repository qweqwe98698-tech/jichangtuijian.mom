新手打开节点列表的第一反应通常是从上往下挨个点、看哪个延迟最低。这个做法有两处代价:一是慢,几十个节点测下来十几分钟就没了;二是贵,测试本身也走流量,而列表里延迟最低的那几条往往正是倍率最高的线路,等于用最贵的方式做了一次筛选。

更省事的顺序是反过来的:先读名字,把候选缩到三五个,再去连。节点名是服务商写给你的说明书,地区、编号、倍率和用途标签都写在里面,只是没人告诉你这些字段怎么读。

这篇就做一件事:把节点名拆成可读的字段,再给一张按用途选节点的对照表,让判断发生在连接之前。

## 节点名里那一串信息分别代表什么?

不同服务商的命名习惯不完全统一,但字段种类高度一致。以一个结构示例为例:

```text
香港 03 | IEPL | 2x | 流媒体
 ↑     ↑     ↑     ↑     ↑
地区  编号  线路   倍率  用途标签
```

对应关系是这样的:

| 字段     | 常见写法                             | 它告诉你什么                                  |
| -------- | ------------------------------------ | --------------------------------------------- |
| 地区     | 香港 / HK / 日本 / JP / 新加坡 / SG  | 落地服务器在哪,决定基础延迟与可访问的地区内容 |
| 编号     | 01、02、03                           | 同地区的第几台机器,用于反馈时定位             |
| 线路类型 | IEPL、IPLC、专线、中转、直连、BGP    | 数据包走的是什么路径,决定晚高峰表现           |
| 倍率     | 0.5x、1x、2x、3x、×5                 | 每传输 1GB 实际扣多少流量                     |
| 用途标签 | 流媒体、Netflix、AI、GPT、家宽、原生 | 这条线被针对性优化或验证过的场景              |

有些名字里还会出现「试用」「临时」「备用」这类词,通常表示这条线的存续期或稳定性预期低于常规节点,不适合作为主力。

## 地区怎么选:近的一定更好吗?

物理距离决定延迟下限,这一点没有例外——香港到内地的往返延迟天然低于美国。但「延迟低」和「好用」是两件事,近的地区同时也是最拥挤的地区。

| 地区         | 典型定位              | 需要注意什么                                |
| ------------ | --------------------- | ------------------------------------------- |
| 香港         | 延迟最低,晚高峰最拥挤 | 优质线路倍率普遍偏高,低倍率节点晚上容易被压 |
| 日本、新加坡 | 延迟稍高,负载相对分散 | 综合体验常比同价位香港节点更稳              |
| 台湾、韩国   | 延迟接近日本          | 可选节点数量通常较少                        |
| 美国         | 延迟明显更高          | 内容生态最全,适合对延迟不敏感的场景         |
| 欧洲及其他   | 延迟最高              | 多为特定内容或特定服务需求才用              |

选地区的实际原则是:先按用途确定必须落在哪个地区(比如某项服务只在特定地区可用),再在候选地区里按延迟和倍率排序。用途没有地区要求时,优先近距离;有地区要求时,地区优先级高于延迟。

线路类型对晚高峰的影响比地区更大,这部分展开在[中转与直连的结构差异](/protocols/how-to-choose/transit-vs-direct/)。

## 倍率标记在哪里看,选错会有多贵?

倍率写在节点名里、节点分组说明里,或者帮助中心的一张表里,三处都要找一遍。它的作用是流量乘数:标 2x 的节点,你传 1GB,套餐扣 2GB。

这个数字对套餐寿命的影响比多数人预估的大。下面是一个纯示例的算法演示,流量数字按常见码率推算,仅作量级参考,不同平台与画质差异很大:

```text
套餐额度            100 GB / 月
看 1 小时 1080p     约消耗 3 GB(参考值)

在 1x 节点上        100 ÷ 3  ≈ 33 小时
在 2x 节点上        100 ÷ 6  ≈ 16 小时
在 3x 节点上        100 ÷ 9  ≈ 11 小时
```

同一份套餐,选错倍率会让可用时长少掉三分之二。这也是为什么「挨个点开测一遍」的代价不只是时间——测试流量同样按倍率扣。

> 建立一个习惯:把日常默认节点固定成低倍率的那一条,只在明确需要时手动切到高倍率线路,用完切回来。流量消耗速度异常时的核算方法在[流量用完了怎么查](/troubleshooting/connection-failed/traffic-used-up/)。

## IEPL、家宽、原生 IP 这些标签各自意味着什么?

这几个词描述的不是同一个维度,混在一起看容易得出错误结论:

| 标签               | 描述的维度   | 实际含义                              | 典型代价                  |
| ------------------ | ------------ | ------------------------------------- | ------------------------- |
| IEPL / IPLC / 专线 | 跨境路径     | 不经过公网国际出口,晚高峰受拥堵影响小 | 倍率高,成本最高的一类     |
| 中转               | 跨境路径     | 先连入口机再转发到落地,路径可优化     | 倍率中等                  |
| 直连               | 跨境路径     | 设备直接连落地,全程走公网出口         | 便宜,晚高峰波动大         |
| 家宽 / 住宅        | 出口 IP 类型 | 出口 IP 归属民用宽带,平台判定更宽松   | 带宽通常受限,不适合大流量 |
| 原生 IP            | 出口 IP 类型 | IP 注册地与节点所在地一致             | 数量少,倍率常偏高         |
| BGP / 多入口       | 接入侧       | 入口机对接多家运营商,换网络时波动小   | 无直接代价,属于服务商基建 |

要点是:线路类型解决的是「快不快、晚上崩不崩」,IP 类型解决的是「目标平台认不认」。两者不能互相替代——专线节点如果出口 IP 被平台标记,照样打不开;原生 IP 节点如果走公网直连,晚高峰照样卡。专线两个缩写的准确定义见[IEPL 与 IPLC 到底指什么](/protocols/how-to-choose/iepl-iplc-explained/),IP 归属的判定逻辑见[原生 IP 和广播 IP 的区别](/protocols/how-to-choose/native-ip-vs-broadcast-ip/)。

## 流媒体标签和 AI 标签的节点,和普通节点差在哪里?

差别几乎不在带宽,而在出口 IP 的选择和路由的稳定性。

带流媒体标签的节点,服务商通常为它挑选了未被目标平台大规模标记的出口 IP,并会在失效后更换。带 AI 标签的节点侧重点不同:AI 工具的对话是长连接,中途换 IP 会被判定为会话异常,所以这类节点更强调出口 IP 在一段时间内保持不变,以及连接不被中途掐断。

需要提醒的是口径问题。这类标签表达的是服务商的优化方向和当时的可用状态,不等于永久有效——平台的检测策略在持续更新,今天可用的出口明天可能被标记。看到「全解锁」这类绝对表述时,合理的理解是「宣称支持」,而不是「已验证且长期成立」。

> 判断一条流媒体或 AI 节点是否真的可用,唯一方法是用你自己的账号在你要用的那个服务上实际打开一次。别人的测试结果不能直接迁移,因为账号状态、地区设置和检测时机都不同。

## 按用途对照:日常浏览、看视频、AI 工具、下载各选什么?

把上面几个维度合起来,就是一张可以直接用的对照表:

| 用途             | 地区取向       | 倍率取向           | 需要的标签          | 主要判断依据              |
| ---------------- | -------------- | ------------------ | ------------------- | ------------------------- |
| 网页浏览、查资料 | 就近(港日新)   | 越低越好,0.5x 优先 | 无                  | 能打开就够,不必追求低延迟 |
| 在线视频         | 内容所在地区   | 低倍率优先         | 流媒体 / 对应平台名 | 稳定不缓冲比峰值速度重要  |
| AI 对话与 API    | 服务支持的地区 | 可接受较高         | AI / 对应工具名     | 出口 IP 是否稳定不漂移    |
| 大文件下载       | 就近           | 必须低倍率         | 无                  | 倍率是第一约束,速度第二   |
| 游戏、实时通话   | 就近           | 可接受较高         | 专线 / IEPL         | 抖动与丢包,不看平均延迟   |
| 网银等敏感操作   | 建议不走代理   | —                  | —                   | 走分流规则排除在代理之外  |

这张表的用法是从右往左读:先确定判断依据,再倒推该找什么标签。AI 工具对节点的具体要求可以进一步看[AI 工具对节点的要求](/unlock/region-lock/ai-node-requirements/)。

## 为什么节点数量多不等于好用?

因为你同时只用一个节点。列表里有 200 条还是 30 条,对单次连接的体验没有直接影响,真正影响体验的是你实际会用的那三五条的质量。

数量多有时反而是负信号。同一地区堆几十个编号,可能意味着单机承载能力有限、需要靠数量分摊;列表里塞满你永远用不上的冷门地区,也可能是在把清单撑得好看。判断质量的实际做法是:只看你会用的那个地区,数一数其中低倍率且稳定可用的有几条——这个数字通常远小于总数。

## 选好之后,用哪两个指标验证这次选择是对的?

两个,都不是峰值速度:

1. **晚高峰时段的可用性**。工作日晚上八点到十一点是负载最高的时段,白天表现好说明不了什么。在这个时段用你实际的用途跑一次,能正常完成就算通过,卡顿或中断就换。
2. **一小时内的中断次数**。保持连接一小时,记录被断开的次数。日常使用中偶尔一次可以接受,反复中断说明这条线不适合做主力,尤其影响 AI 对话和大文件下载这类不能中途断的任务。

这两项都通过,再把这条节点固定为默认。都不通过而同地区其他节点也一样,那问题就不在节点选择这一层了,该往[延迟与丢包的分开测量](/troubleshooting/connection-failed/latency-high-and-packet-loss/)或[晚高峰变慢的成因](/troubleshooting/connection-failed/speed-slow-at-peak-hours/)方向走。

## 小结

节点名是服务商写好的说明书,地区、线路、倍率、标签四个字段读完,候选范围就能从几十条缩到三五条。倍率是唯一一个选错会持续付出代价的字段,日常默认节点务必固定在低倍率线路上。线路类型决定晚高峰稳不稳,出口 IP 类型决定平台认不认,两者不能互相替代。标签只代表服务商的优化方向,是否可用要用自己的账号实测一次。最后用晚高峰可用性和一小时中断次数两项验证,通过了再固定下来。
