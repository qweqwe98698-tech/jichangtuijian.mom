单点故障这个词在运维里人人都懂，放到个人网络上却经常被忽略。你把所有跨境流量交给一家服务商，等于把可用性、你的订阅地址、你的余额和你的使用连续性全押在同一个决策上。这个决策在 99% 的日子里都没问题，问题出在剩下那 1%——而那 1% 往往集中在最需要网络的时刻。

冗余的思路和买保险不一样。保险是出险后赔钱，冗余是**故障时不中断**。这两者的区别决定了备用位该怎么配：它不需要和主力同样好，只需要在主力不可用的那几个小时到几天里，把你的关键任务撑住。一旦接受这个定位，成本立刻降下来——你要买的不是第二个主力，是一个待命的替补。

这篇不讨论"哪家更好"，只讨论组合本身：增量花多少钱、备用位用哪种计费方式、两家该在哪些属性上刻意错开、客户端里怎么配置才不用临时重来，以及什么人可以跳过这一整套。

## 只买一家机场的真实风险是什么？

把"用不了"这件事拆开，会发现它有四种完全不同的成因，恢复时间也完全不同：

| 故障类型                   | 典型持续时间   | 是否有预警 | 单线用户的处境                             |
| -------------------------- | -------------- | ---------- | ------------------------------------------ |
| 节点或落地临时故障         | 几分钟到几小时 | 无         | 换节点通常能解决，风险最低                 |
| 大规模封锁导致整批线路失效 | 数小时到数天   | 无         | 全部节点同时不可用，只能等                 |
| 官网或订阅地址被墙         | 数小时到数周   | 无         | 客户端里的旧节点可能还能连，但无法更新订阅 |
| 服务商停运或跑路           | 永久           | 有时有迹象 | 余额归零，需要从零开始挑选和配置           |

第三种最容易被低估。订阅更新失败时，很多人第一反应是客户端出了问题，实际上是拉取订阅的那个地址本身连不上了——而拉订阅这个动作往往需要先有可用的代理，形成一个死循环。手上有第二份还能用的订阅，这个循环就直接解开了。

第四种则是纯粹的资金和时间损失。跑路当天你要做的事情是：找新机场、比价、下单、导入订阅、重配规则、重新测节点，顺利也要一两个小时，且这一两个小时里你是完全断网的。

## 主备双线的增量成本大概是多少？

按各家公开资料里的入门套餐算一笔账。本站收录的 16 家中，按月计价的入门套餐大致落在 14.9 元到 25 元区间，另有两家以年付折算价标示，折合每月 7 至 8 元。备用位不需要买中高档，最低档就够。

| 方案                      | 主力支出    | 备用位支出      | 月度合计    | 相对单线的增量 |
| ------------------------- | ----------- | --------------- | ----------- | -------------- |
| 只买一家（中档月付）      | 约 20 元    | 0               | 约 20 元    | 基准           |
| 主力中档 + 备用最低档月付 | 约 20 元    | 约 15 元        | 约 35 元    | 约 +75%        |
| 主力中档 + 备用按量套餐   | 约 20 元    | 摊薄后约 3–6 元 | 约 23–26 元 | 约 +15%–30%    |
| 主力年付 + 备用按量套餐   | 折算约 8 元 | 摊薄后约 3–6 元 | 约 11–14 元 | 约 +40%–75%    |

> 上表的金额来自各家厂商公开的入门套餐标价，用于说明数量级，不是实测消费记录。按量套餐的月度摊薄值取决于你实际用掉多少，以及一份预付包能撑几个月，个人差异很大。年付折算价与月付价不可直接比较，前者要求一次性支付全年。

关键结论在第三行：**用按量套餐做备用位，增量通常只有两三成，而不是翻倍**。翻倍的那种配置（两个月付套餐并行）只有在你确实需要两条主力线时才合理，比如家里和公司要长期分开走不同出口。

## 为什么备用位适合用按量计费套餐？

因为备用位的使用特征和按量计费的计价逻辑刚好吻合：**长时间零消耗，偶尔集中使用**。

按月计费的套餐每个月都在扣钱，无论你用没用；按量计费卖的是一份不与自然月绑定的流量额度，用多少扣多少。一份备用位一年可能只被真正启用三四次、每次几天，落到按量模式下的总支出，往往还不如两个月的月费。

不过这里有几个必须先确认的条款，否则"不用就不扣"会变成"用不上"：

| 需要确认的条款             | 为什么重要                        | 不合格时的后果           |
| -------------------------- | --------------------------------- | ------------------------ |
| 流量包是否有有效期         | 很多"按量"其实带 6 或 12 个月上限 | 到期清零，等于白买       |
| 长期不活跃是否会被回收账号 | 部分服务商会清理僵尸账号          | 要用时发现账号已注销     |
| 订阅地址是否长期有效       | 地址重置会让客户端里的配置失效    | 需要重新登录后台取新地址 |
| 节点倍率如何计费           | 高倍率节点会让额度消耗远快于预期  | 应急时额度几小时就见底   |

两种计费模式各自把风险放在哪一端，[按量计费和不限时套餐的取舍](/compare/how-to-choose-airport/pay-as-you-go-vs-unlimited-time/)那篇有完整比较。这里只需要记住：备用位要的是"能随时启用"，所以有效期和账号活跃度的条款比单价更重要。

## 主备两家应该在哪些属性上刻意错开？

冗余的全部价值建立在一个前提上：两家不会同时出问题。如果两家的技术栈和上游高度重合，你买的就不是冗余，是同一个故障的两份副本。下面这些属性应该主动错开：

| 属性               | 为什么要错开                         | 错开的做法                                                      |
| ------------------ | ------------------------------------ | --------------------------------------------------------------- |
| 主用协议           | 某类协议特征被针对时会整批失效       | 主力用 TCP 系（如 Trojan/VLESS），备用带 UDP 系（如 Hysteria2） |
| 线路类型           | 专线与公网中转的失效原因不同         | 主力走专线或优质中转，备用用直连或另一类中转                    |
| 落地区域           | 单一区域出问题时不至于全线瘫痪       | 主力香港/日本，备用新加坡/美西                                  |
| 运营年限           | 分散服务商级别的经营风险             | 主力选运营记录长的，备用可放新面孔试水                          |
| 支付与登录方式     | 支付渠道被限制时不至于两边都续不上费 | 尽量不集中在同一个支付通道                                      |
| 官网域名与订阅域名 | 域名批量失效时保留一条可更新的通道   | 提前把两家的订阅地址各存一份到本地                              |

前两项最重要。协议和线路类型不同，意味着两条线对同一次网络环境变化的敏感度不同——这正是你花那两三成钱想买到的东西。运营年限那一项可以和[老牌与新机场的分工](/compare/how-to-choose-airport/veteran-vs-new-airport/)结合起来：主力位交给有抗风险记录的，备用位顺便当作新机场的试水位，一举两得。

## 客户端里怎么安排主备切换才不用重配？

正确的做法是**提前配好，而不是出事时再配**。主流客户端都支持多订阅并存，把两份订阅同时放进去，用一个策略组统一切换，故障时只需要动一下选择器。按下面的顺序做一次，之后就不用再管：

1. **把两份订阅都导入客户端**。多数客户端的配置或订阅页面支持添加多条，导入后各自保留独立的更新周期。这一步的目的是让备用节点在故障发生前就已经躺在配置里，不依赖临时下载。
2. **建立一个手动选择的顶层策略组**。让它的候选项是"主力组"和"备用组"两个子组，而不是几十个具体节点。切换时你只需要在顶层动一次，所有规则都会跟着走。
3. **主力组内用自动测延迟，备用组内也一样**。这样启用备用时不需要再手工挑节点，进组即可用。
4. **规则分流保持在顶层策略组之上**。分域名、分应用的规则应该指向顶层组，而不是指向某个具体节点，否则换机场时每条规则都要改。
5. **把两家的订阅地址离线备份一份**。存在本地文本文件或密码管理器里，不要只存在客户端里——客户端配置损坏时你需要它。
6. **给两个组各留一个可用的备用端口或协议入口**。同一家机场通常提供多种协议的订阅，把不同协议的那份也加进来，成本为零。

下面是策略组的结构示例，用 Clash 类客户端的配置片段表示，服务器地址一律用占位域名：

```yaml
# 结构示例，非可用配置；example.invalid 为占位域名
proxy-groups:
  - name: '总出口' # 规则全部指向这一层
    type: select
    proxies: ['主力', '备用', 'DIRECT']

  - name: '主力'
    type: url-test
    use: ['sub-primary'] # 来自主力机场的订阅
    url: 'http://cp.example.invalid/generate_204'
    interval: 300

  - name: '备用'
    type: url-test
    use: ['sub-standby'] # 来自备用机场的订阅
    url: 'http://cp.example.invalid/generate_204'
    interval: 300
```

具体到界面上每一步点哪里，[Clash 系客户端的使用专题](/guides/clash/)和[小火箭的配置专题](/guides/shadowrocket/)里有分步说明；iOS 端的策略组名称和这里不同，但分层思路一致。

## 备用线路多久验证一次才不会"到用时才发现失效"？

备用位最常见的失败模式不是不够快，是**根本连不上**——订阅地址被重置了、账号因长期不活跃被清理了、流量包过期了。这些都不会有人通知你。

一份低成本的验证节奏是这样的：

| 频率           | 要做的事                                         | 大约耗时 |
| -------------- | ------------------------------------------------ | -------- |
| 每月一次       | 手动刷新备用订阅，确认节点数量正常               | 1 分钟   |
| 每季度一次     | 切到备用组实际用半小时，跑一次你最依赖的服务     | 30 分钟  |
| 每半年一次     | 登录备用机场后台，确认账号状态、剩余额度与有效期 | 5 分钟   |
| 主力出现异常后 | 立即完整验证一次备用，不要假设它还好             | 15 分钟  |

> 千万不要在主力已经出问题的时候才第一次启用备用。那时你同时面对两个未知：主力为什么坏、备用能不能用。季度性的半小时演练，成本极低，但它把"备用可用"从假设变成了事实。

## 哪些用户其实不需要冗余配置？

冗余不是所有人的必需品。下面这几种情况，把钱花在单线的更高档位上更划算：

- **纯娱乐用途，断一两天没有任何实际损失**。这种情况下故障的成本接近于零，而备用位的成本是持续的。
- **月流量很小、使用极不规律**。一个月只用几个小时的人，直接买一份按量套餐当唯一线路就够，本身已经具备低成本重来的能力。
- **预算非常有限，二选一会拉低主力档位**。如果加备用位意味着主力必须降到明显不够用的档位，那是在用确定的体验下降换不确定的可用性。
- **所在网络环境本身就有替代通道**，比如工作场景另有由单位提供的合规访问方式，那条通道天然充当了备用。

反过来，只要你的收入、工作交付或长时间的 AI 会话依赖这条线路，冗余就是必需的，而且应该在主力还好用的时候就配好。

## 小结

单线的风险不在于贵，在于故障和停运时你没有第二条路，而恢复过程恰好发生在你最需要网络的时候。备用位的定位是替补而非第二主力，因此最低档的按量套餐通常就够，增量成本落在主力的两三成而不是翻倍。两家要在协议、线路类型、落地区域和支付通道上刻意错开，否则一次事件会把两条线一起打掉。客户端里用一个顶层策略组把两份订阅统一管起来，规则全部指向这一层，切换就只剩一次点击。最后是最容易被跳过的一步：每季度花半小时真正用一次备用线路，否则它只是一份让你安心的假象。
