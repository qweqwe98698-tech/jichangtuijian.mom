这是小火箭最容易让人误判的一种状态:开关是绿的,状态栏顶上挂着 VPN 标记,节点列表里延迟数字也测出来了,浏览器却始终停在转圈。看起来一切正常,实际什么都传不过去。

问题出在「已连接」这三个字的含义被高估了。它证明的只是系统已经把网络流量交给小火箭处理,是一个本地状态,和远端节点是否活着没有必然关系。节点在半夜被封、机房掉线、落地服务停了,状态栏那个标记照样亮着。

也正因为这样,遇到假连接不该立刻重装 App 或者换机场——那是成本最高、命中率最低的两个动作。真正有效的做法是用三次操作把可能性收敛掉,每一次都排除一整类原因。

## 延迟能测出来,为什么不代表节点能用?

延迟测试做的事情比大多数人想象的要少。它通常只验证到「能不能和节点建立连接」这一层,握手完成就报出毫秒数,并不真的经由节点去访问一个外部网站再回来。

于是就有了这种错位:节点服务器还在监听端口,握手正常,但它到境外目标的那段链路已经断了,或者落地 IP 被目标站点拒绝。测速看起来漂亮,数据一条也过不去。

| 你看到的现象                        | 最可能的原因                    | 用什么动作验证             |
| ----------------------------------- | ------------------------------- | -------------------------- |
| 全部节点都测得出延迟,全部打不开网页 | 路由模式或 DNS 层出问题         | 切换路由模式复测           |
| 只有某一个节点这样,换一条就好       | 该节点后端失效                  | 换同地区其他节点           |
| 境外能开、国内站点变慢              | 国内流量也被送进了节点          | 检查是否处于代理或全局模式 |
| 部分网站正常、部分一直转圈          | 域名被规则判成直连,或解析被污染 | 检查 DNS 与规则命中        |
| 刚连上能用几分钟后失效              | 节点被限速或连接被中断          | 观察是否只在特定时段发生   |

## 三分钟定位法:换节点、换模式、查 DNS

顺序是有讲究的——把验证成本最低、覆盖面最广的动作放前面:

1. **换一个不同地区的节点**。别在同一地区里换编号,那些节点常在同一机房,同生共死。香港不行就试日本或美国,一步跨开。这一步能排掉「单节点失效」这一整类原因,花不到十秒。
2. **切到代理模式复测**。如果换了地区仍然不通,把路由从「配置」切成「代理」,让几乎所有流量都走节点。这一步是在区分「节点问题」和「规则问题」。
3. **检查 DNS 设置**。前两步都无效时,才轮到 DNS。把 DNS 改成配置默认或机场推荐值,再重连一次。

> 三步都做完仍然不通,再考虑重启 App 或重启手机。顺序反过来做——先重装、先换机场——你会浪费掉大量时间,而且即便碰巧恢复了,也不知道刚才到底是什么坏了。

## 切到代理模式就好了,说明什么?

这个结果的信息量很大:节点是好的,流量出得去,问题在**分流判断**上。也就是说,「配置」模式下的某条规则把你要访问的域名判给了直连,而这个域名在国内直连是打不开的。

常见成因有两个。一是规则集本身老旧,没收录较新的域名;二是自己往靠前的位置插过一条规则,匹配范围写得太宽,顺带把目标域名一起吃掉了。规则是自上而下匹配、第一条命中即生效的,位置比内容更容易出错。

处理办法是回到规则列表,在国内直连规则组**之前**补一条针对该域名的代理规则,而不是干脆长期停在代理模式。长期用代理模式的代价是国内网站、外卖和视频 App 会明显变慢,套餐流量也消耗得更快。

## 只有部分网站打不开,其他正常呢?

这种情况几乎可以确定与节点无关。既然大部分站点通,说明隧道是活的,剩下的可能性集中在三处:

- 目标域名被规则判成了直连,前一节讲的就是它。
- 目标站点识别到落地 IP 属于机房段,主动拒绝——流媒体和部分 AI 服务对这一点尤其敏感,表现常是打得开首页但登录或播放报错。这类判定逻辑在 [流媒体与 AI 访问栏目](/unlock/) 里有专门说明。
- 该站点自身故障,和你的网络无关。用另一条完全不同的网络路径复核一下,比反复调设置更省事。

## DNS 出问题时会有哪些表现?

DNS 负责把域名翻译成 IP,它坏掉的样子很有辨识度:浏览器提示「找不到服务器」而不是「连接超时」;同一个站点用 IP 能访问、用域名不能;或者刚连上时能打开,过一会儿全部域名都解析失败。

小火箭里的 DNS 设置项如果被改成了一个当前网络不可达的服务器,结果就是所有请求卡在解析这一步——隧道明明是通的,但没有一个域名能变成 IP。清空回默认值再连一次,是这一类问题成本最低的处理方式。

## 关掉再打开就临时恢复,是什么在起作用?

重连会重建隧道并清掉本地的连接缓存与解析缓存。如果每次都能靠这个动作短暂恢复,说明失效是渐进发生的,而不是配置写错了——配置错误不会时好时坏。

渐进失效通常指向两类原因:节点在使用一段时间后被限速或被中断,或者本地缓存里存了一批已经失效的解析结果。前者要换节点观察,后者可以在重连后留意能撑多久,时长本身就是线索。

## 反复出现假连接,该继续修还是换机场?

值得区分两种情况。偶尔一两条节点失效是常态,任何服务都会有;但如果换过地区、换过模式、清过 DNS,不同时间段都复现,而且订阅更新后新节点同样如此,那问题基本落在服务端。

判断前先确认订阅本身是新鲜的:很多长期假连接其实是订阅很久没更新,列表里全是早已下线的旧节点。导入与刷新的完整流程写在 [Shadowrocket 导入订阅的三种方式](/guides/shadowrocket/shadowrocket-import-subscription/);如果连 App 都还没配置好,可以先看 [小火箭下载与购买渠道说明](/guides/shadowrocket/shadowrocket-download-and-install/)。确认是服务端持续性问题之后,再到 [机场评测栏目](/reviews/) 对照各家公开的线路类型和协议规格,判断换一家是否真能解决你遇到的问题。其他现象(节点整片超时、国内网站变慢)属于不同的排查路径,可在 [故障排查栏目](/troubleshooting/) 按现象对号入座。

## 小结

「已连接」是本地状态,不是连通性证明,延迟数字同样只说明握手成功。遇到假连接,按换地区节点、切代理模式、查 DNS 的顺序走一遍,三步分别排除节点失效、规则误判和解析故障三类原因。切到代理模式就恢复,说明该修的是规则而不是节点,修完要切回「配置」模式,否则国内访问会被拖慢。反复复现且订阅已是最新时,问题才落在服务端。
