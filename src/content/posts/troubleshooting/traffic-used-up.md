这一篇处理的不是技术故障。节点没坏、线路没断、客户端也没配错,只是你的账户已经不再被允许转发数据了。之所以它值得单独写,是因为在客户端界面上,「欠费」和「故障」长得一模一样:节点列表照常刷新,延迟测试可能还有数值,可网页就是打不开。

于是很多人在这里浪费掉一两个小时,重导订阅、换节点、重装客户端、检查系统代理,把所有和连通性有关的动作做了一遍。而真正需要的操作只有一个——打开用户中心看一眼剩余流量。

计费这件事之所以容易算错,是因为它有三个不那么直观的规则:倍率会让扣除量成倍放大、上传和下载合并计入同一个额度、重置日期未必是每月一号。这三条搞清楚,大部分「流量掉得莫名其妙」都能解释。

## 先分清:是流量用完,还是节点真出问题

两者的现象重叠度很高,但有几处可以直接分开:

| 观察点       | 流量耗尽             | 节点故障             |
| ------------ | -------------------- | -------------------- |
| 订阅能否更新 | 能,节点数量正常      | 常常连订阅都拉不下来 |
| 节点失效范围 | 全部节点一起         | 通常只有部分地区     |
| 延迟测试     | 可能仍有数值         | 多为红色超时         |
| 换设备后     | 同样失效             | 视原因而定           |
| 用户中心     | 剩余量接近零或已归零 | 剩余量正常           |
| 恢复时点     | 重置日或充值后       | 不确定               |

第一行是最有价值的一条。订阅链接返回的只是一段配置文本,体积以 KB 计,通常不走计费通道,所以流量耗尽时它照样能更新。「订阅正常刷新但所有节点都不能用」这个组合,几乎就是流量耗尽的专属指纹。

如果订阅本身也拉不下来,那是另一类问题,该走[排查总览](/troubleshooting/connection-failed/)的流程。

有些订阅链接在响应头里直接带着用量信息,能省掉登录面板的步骤。下面是这个响应头的结构示例,数字为示意值,地址用 `example.invalid`:

```http
subscription-userinfo: upload=5368709120; download=48318382080; total=107374182400; expire=1767225600
```

四个字段分别是上传字节数、下载字节数、套餐总量、到期时间戳。把上传和下载相加除以总量,就是已用比例——这也顺带证明了一件事:上传是计费的。

## 倍率怎么换算

倍率是一个乘数,决定实际传输的每一个字节从额度里扣掉多少。它不影响速度,只影响扣费。

| 倍率       | 传输 1 GB 实际扣除 | 100 GB 额度可传输 | 常见于                   |
| ---------- | ------------------ | ----------------- | ------------------------ |
| 0.2        | 0.2 GB             | 500 GB            | 促销节点、备用出口       |
| 0.5        | 0.5 GB             | 200 GB            | 部分直连或大带宽线路     |
| 1.0        | 1 GB               | 100 GB            | 标准中转,最常见          |
| 2.0        | 2 GB               | 50 GB             | 优质中转、部分流媒体线路 |
| 3.0 及以上 | 3 GB 以上          | 33 GB 以下        | 跨境专线、稀缺地区       |

换算本身很简单:

```text
实际扣除 = 传输量 × 节点倍率

例:在 2 倍节点上看完一部 1080p 影片,传输约 3 GB
    实际扣除 = 3 × 2 = 6 GB
    同样内容在 1 倍节点上只扣 3 GB
```

真正的坑在于混用。多数人不会全程用同一个节点——白天用 1 倍的工作节点,晚上切到 3 倍的专线看视频,月底一算发现和预期差了一倍多。而面板只给一个总数,不会按节点拆分,所以你看不出这个差额是从哪里来的。

> 倍率标记通常写在节点名里,形如末尾的 `x2`、`2.0x` 或中文的「倍率」字样,各家写法不统一。切节点之前扫一眼这个标记,是最省钱的一个习惯。把整套套餐折成每 GB 实际单价的算法,在[性价比换算方法](/compare/how-to-choose-airport/value-calculation/)里。

## 为什么专线和流媒体节点的倍率更高

因为它们的成本结构不同。跨境专线是向电信运营商采购的企业级线路,按带宽包月计费,单位成本远高于普通公网中转;流媒体优化线路则往往需要维护特定归属的出口 IP,这类 IP 的获取和保有成本也高于普通机房 IP。

倍率就是把这部分成本差转嫁到用量上的手段。它比「专线单独卖」更灵活——用户想用就切过去,不想用就切回普通节点,不必为不常用的能力常年付费。

| 节点类型   | 成本来源       | 倍率倾向     | 适合的用法       |
| ---------- | -------------- | ------------ | ---------------- |
| 普通中转   | 公网带宽       | 1 倍上下     | 日常浏览、办公   |
| 大带宽直连 | 批发带宽       | 0.5 倍及以下 | 大文件下载       |
| 跨境专线   | 运营商专线租用 | 2 倍以上     | 会议、低延迟需求 |
| 流媒体优化 | 特定归属 IP    | 视各家而定   | 只在需要时切过去 |

专线为什么贵、它和「优质中转」的技术差别在哪,可以看[IEPL 与 IPLC 的定义说明](/protocols/how-to-choose/iepl-iplc-explained/)。

## 重置什么时候发生

这是第二个高频误解来源。「每月重置」并不等于「每月一号重置」。

| 重置口径 | 重置时点             | 常见于                 | 注意                          |
| -------- | -------------------- | ---------------------- | ----------------------------- |
| 按购买日 | 每月与首次付款同一天 | 多数月付套餐           | 月底告急的日期每月固定        |
| 按自然月 | 每月一号零点         | 部分套餐               | 首月为不足月,额度可能按比例给 |
| 不重置   | 无周期,用完为止      | 按量套餐、一次性流量包 | 只受有效期限制                |
| 手动重置 | 用户付费触发         | 提前重置服务           | 通常不叠加,而是直接归位       |

年付套餐要单独说。它绝大多数情况下仍是每月重置一次,而不是一次性给全年额度——你买的是十二个月的使用权和一个折扣,不是十二倍的月流量。少数标称年度总量的套餐才是一次给全,这种情况下用完就没有,和月度重置的容错度完全不同。

购买前值得确认的两点:重置的具体日期是哪一天,以及重置时剩余流量是清零还是累计。前者决定你怎么安排大流量任务,后者决定省下来的额度有没有意义。绝大多数月付套餐不结转。

## 上传也计费,以及那些悄悄吃流量的行为

面板上的上传和下载是两个数字,扣的是它们的和。这一条解释了很多「我没下载什么啊」的困惑。

以下是按常见码率与文件体积推算的参考值,用来建立量级概念,实际消耗受清晰度设置、平台压缩策略和使用习惯影响,差异可能很大:

| 行为                   | 每小时参考消耗 | 方向       |
| ---------------------- | -------------- | ---------- |
| 网页浏览、文字聊天     | 100–300 MB     | 以下行为主 |
| 音乐流媒体             | 50–100 MB      | 下行       |
| 1080p 视频播放         | 2–3 GB         | 下行       |
| 4K 视频播放            | 7–11 GB        | 下行       |
| 视频会议               | 1–2 GB         | 上下行接近 |
| 云盘同步大文件夹       | 取决于文件量   | 以上行为主 |
| 上传一段十分钟手机视频 | 单次 1–2 GB    | 上行       |

真正需要警惕的是那些不需要你参与的消耗。它们全天候运行,而且很容易在全局代理模式下被一并送进代理链路:

1. **系统与应用的自动更新。** 一次大版本更新几个 GB 是常态,而它挑的时间往往是夜里。
2. **云盘与相册同步。** 手机自动备份原图和视频,是上行流量最大的单一来源。
3. **视频平台的预加载。** 播放器会提前缓冲后续内容,你切走了但已经下载的部分照样计费。
4. **应用商店的后台下载。** 多个应用同时更新时,几分钟就能吃掉几个 GB。
5. **种子类软件的做种上传。** 这一项的上行消耗可以是无上限的。

> 处理办法不是逐个关掉,而是用规则把它们排除出代理。把系统更新域名、云盘客户端、下载工具走直连,既省流量也省钱。规则怎么配,各客户端的做法可以看 [Clash 专题](/guides/clash/)、[Shadowrocket 专题](/guides/shadowrocket/)和 [v2rayN 专题](/guides/v2rayn/)。

另外,全局代理模式是流量消耗的放大器。它会把所有流量都送出去,包括本可以直连的国内服务。改用规则分流,通常能立刻省下三到五成。

## 加油包、提前重置、升级套餐,怎么选

三个选项适用的场景完全不同,选之前先回答一个问题:这次超支是偶发,还是已经连续发生了两三个周期?

| 方案         | 适合的情况           | 优点              | 需要注意                   |
| ------------ | -------------------- | ----------------- | -------------------------- |
| 等到重置日   | 距离重置只剩几天     | 零成本            | 期间基本不可用             |
| 买加油包     | 偶发超支,量不大      | 一次性,不改变套餐 | 单位价格通常高于套餐内流量 |
| 提前重置     | 距重置日还很久       | 立刻恢复满额      | 剩余流量通常被清零而非叠加 |
| 升级套餐     | 连续多个周期超支     | 单位价格更低      | 需确认差价怎么结算         |
| 启用备用线路 | 主力已耗尽且不想加钱 | 不中断使用        | 需要提前准备好第二份订阅   |

第三行有个容易吃亏的地方:提前重置多数是把额度「重设」为套餐值,而不是在剩余量上加一份。如果你还剩 20 GB 就去重置 100 GB 的套餐,结果是 100 GB 而不是 120 GB,那 20 GB 就没了。距离重置日还有很久时这笔账才划算。

判断该不该升级,把两种方案折成每 GB 单价直接比就行。如果你的用量长期偏高,从一开始就选大流量档位比反复补票便宜,[大流量维度的排行榜](/rankings/big-traffic/)可以作为候选范围。

最后提一句归因:如果恢复流量之后速度依然不理想,那说明流量耗尽只是叠加在原有问题上的一层。晚高峰的吞吐劣化要按[慢的排查流程](/troubleshooting/connection-failed/speed-slow-at-peak-hours/)处理,卡顿和断连则要去测[延迟、抖动与丢包](/troubleshooting/connection-failed/latency-high-and-packet-loss/),两者的成因和计费毫无关系。

## 小结

流量耗尽是计费问题,不是技术问题,判据是订阅照常更新而所有节点一起失效。倍率是乘数,只影响扣除量不影响速度,而混用不同倍率的节点是账对不上的首要原因。重置日多数按购买日而非自然月,年付套餐同样是每月重置,剩余流量绝大多数不结转。上传与下载合并计入同一个额度,云盘同步和视频上传的消耗常常超过看视频本身。真正有效的省流做法是把系统更新、同步类应用和国内服务用规则排除出代理,而不是事后反复买加油包。
