Hysteria2 和 TUIC 的共同点比差异多得多:都跑在 QUIC 上,都用 UDP 承载,都能做连接迁移,都自带多路复用。把它们放在一起比,不是比谁的技术更新,而是比两种截然不同的性格。

QUIC 本身只规定了「怎么在 UDP 上做一条可靠的加密连接」,没有规定「网络开始丢包时该退多少」。这个退让幅度由拥塞控制算法决定,而它恰好是决定实际体感的关键——同一条线路上,两个只有拥塞控制不同的实现,跑出来的速度可以差好几倍。

Hysteria2 的选择是尽量不退。它默认使用一套按你声明的带宽主动发包的策略,遇到丢包不会大幅降速,而是继续按预设速率推送并补发丢失的部分。TUIC 的选择是守规矩,行为更接近标准 QUIC 的拥塞控制,丢包时按算法正常退让,和链路上的其他流量共享带宽。

## 都基于 QUIC,分歧点究竟在哪里

传统的 TCP 系拥塞控制有个内建假设:丢包意味着网络拥堵,所以应该降速。这个假设在数据中心之间成立,在跨境链路上经常不成立——那里的丢包很多来自链路质量、设备策略或干扰,和「拥堵」无关。按拥堵去退让,结果就是明明还有带宽,速度却被自己压下去了。

| 维度             | Hysteria2                         | TUIC                           |
| ---------------- | --------------------------------- | ------------------------------ |
| 拥塞控制取向     | 按声明带宽主动发送,丢包不大幅退让 | 贴近标准 QUIC,按算法正常退让   |
| 对丢包的解读     | 视为链路噪声,补发即可             | 视为需要退让的信号             |
| 需要手动配置带宽 | 通常需要,填错影响明显             | 一般不需要                     |
| 与同链路其他流量 | 抢占性强                          | 相对公平                       |
| 连接迁移表现     | 支持,恢复速度中规中矩             | 支持,切换时更平滑              |
| 典型强项场景     | 高丢包跨境链路的吞吐              | 移动网络、频繁切换、多设备共享 |

「抢占性强」这一行是双刃的:它意味着在你家里那条被室友同时占用的宽带上,Hysteria2 会拿到更多带宽;也意味着如果你自己同时开着别的下载,它会把两边都挤得不舒服。

## 激进的拥塞控制适合什么样的链路

把链路特征和两者的表现对应起来看:

| 链路特征           | Hysteria2 的表现          | TUIC 的表现           |
| ------------------ | ------------------------- | --------------------- |
| 丢包明显、带宽充裕 | 优势最大,能把带宽用起来   | 速度被拥塞控制压住    |
| 链路干净、延迟低   | 与 TUIC 差别很小          | 与 Hysteria2 差别很小 |
| 带宽本身就紧张     | 主动发包造成排队,抖动上升 | 表现更稳              |
| 网络地址频繁变化   | 能恢复,但过程略粗糙       | 恢复更平滑            |
| 本地对 UDP 有限速  | 表现急剧劣化              | 同样劣化              |

最后一行是所有 UDP 类协议的共同软肋,单独展开在 [UDP 被限速的判断与回退](/protocols/how-to-choose/udp-quic-blocked/)里。选协议之前先确认这一条,否则后面的比较全部没有意义。

## 手机切换网络时谁恢复得更快

传统 TCP 连接用「源 IP + 源端口 + 目标 IP + 目标端口」这四项来认一条连接。手机从 Wi-Fi 切到蜂窝数据,源 IP 变了,这四项就对不上,连接必然断掉重连——表现为视频卡住几秒、聊天软件转圈、下载从头再来。

QUIC 改用一个独立的连接标识,地址变了连接标识不变,所以理论上会话可以直接续上。两者都实现了这个能力,差别在细节:TUIC 在设计上对多路复用和连接保持的处理更细致,切换后各条子流恢复得更整齐;Hysteria2 也能恢复,但它的发送策略是按预设带宽推的,切换到一条特性完全不同的网络后,需要一小段时间才能重新贴合实际情况,这段时间里可能出现明显抖动。

> 判断自己是不是这类用户很简单:回想一天里有多少次是在移动中使用——通勤路上、进出办公室、地铁进出站。如果这类场景占多数,切换平滑度比峰值速度更值得优先。

## 丢包率到多少才值得切过来

先用一次可复现的测量拿到数字,再决定:

1. **挑一个平时最常用的节点**,记下它的地区和线路标记。
2. **对该节点服务器持续 Ping 至少 200 个包**,记录丢包率和延迟波动范围。晚高峰和白天各测一次,不要只测一次就下结论。
3. **同一时段用同一节点跑一次下载**,记下稳定速率的中位数,而不是峰值。
4. **切到同机器的 TCP 系协议再测一遍**,保证地区、时段、测试文件都一致。
5. **对比两组数据**,如果 UDP 系明显更高,再考虑长期切换。

一个可供参考的经验区间(不是实测结论,不同网络差异很大):

| 持续丢包率         | 参考判断                            |
| ------------------ | ----------------------------------- |
| 低于 1%            | TCP 系协议已经够用,切过来收益不明显 |
| 1%–5%              | 开始出现差距,值得实测对比           |
| 5% 以上            | 激进拥塞控制的优势通常比较明显      |
| 时高时低、剧烈波动 | 先怀疑本地 UDP 被限速,而不是选协议  |

> 上表是按常见链路情况给出的参考区间,用于划定「值不值得测」的范围,不能替代你自己在自己网络上的测量。

## 为什么有人换了反而更卡

这是 Hysteria2 最常见的翻车方式,原因基本集中在三处:

- **带宽值填得过高**。它按你声明的数值发包,声明 500 Mbps 而实际只有 50 Mbps,多出来的部分全部堆在路上排队,延迟和抖动一起上升。填一个偏保守的实际值,体感往往比填大值更好。
- **本地 UDP 被限速**。校园网、公司网和部分移动网络会对 UDP 做 QoS,激进发包在这种环境下等于往一个被掐细的管子里猛灌,结果是大量重传。
- **把协议当成速度来源**。线路本身就慢的时候,换任何协议都不会变快。协议在总速度里的权重排序,[速度归因的拆解](/protocols/how-to-choose/protocol-speed-myth/)里说得更完整。

## UDP 类协议会更费流量吗

分两部分看。固定开销部分很小:QUIC 的包头和握手材料带来的额外字节,占比通常低到不值得计较。变动部分才是关键——重传。

假设一部按常见码率推算约 1.5 GB 的影片,在两种链路上的计费流量差异大致是这个逻辑:

| 情况                    | 额外流量来源        | 相对量级(推算参考) |
| ----------------------- | ------------------- | ------------------ |
| 干净链路                | 仅协议固定开销      | 接近内容本身大小   |
| 中等丢包 + 保守拥塞控制 | 必要重传            | 略高               |
| 中等丢包 + 激进拥塞控制 | 必要重传 + 主动补发 | 明显更高           |

也就是说,Hysteria2 在坏链路上换来的速度,一部分是用额外流量买的。如果你的套餐流量本来就紧张,这笔账要算进去。倍率高的节点上,这个代价还会再乘一次。

## 手机和电脑分别更适合哪一个

不必绝对化,按主要使用形态挑:

- **手机为主、经常在移动中使用**:优先 TUIC,切换平滑带来的体感收益比峰值速度更实在。
- **电脑为主、固定在家或办公室**:如果这条宽带的跨境丢包明显,Hysteria2 更能把带宽用起来。
- **宽带带宽本来就小**:选 TUIC,激进发包在窄管子里只会制造排队。
- **流量套餐紧张**:选 TUIC,或者干脆用 TCP 系协议。
- **所在网络对 UDP 有限制**:两个都不选,先做限速判断再谈。
- **两种都想留**:完全可以,它们通常跑在同一批服务器上,切换成本只是点一下。

## 小结

这两者的技术底座是同一个,真正分开它们的是面对丢包时退不退让。Hysteria2 选择不退,因此在丢包明显的跨境链路上能把带宽用起来,代价是需要正确填写带宽值、对窄带宽环境不友好、坏链路上的计费流量更高。TUIC 选择按标准行为退让,换来的是移动网络切换时更平滑的恢复和更省的流量。决定前先测一次自己的持续丢包率,并确认本地没有对 UDP 做限速——这两件事没做清楚,协议怎么选都是猜。
