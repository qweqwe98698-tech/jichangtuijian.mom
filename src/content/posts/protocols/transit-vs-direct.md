两个节点都写着"香港",延迟一个 45 毫秒一个 180 毫秒,晚上八点之后差距还会拉得更开。很多人第一反应是机房不同或者带宽不同,其实两者的机房可能就在同一栋楼里。差别在于数据包从你的设备走到那台机器,中间经过了哪几段路。

把整条链路拆开看,任何一次访问都至少经过三段:你的设备到接入点、接入点到落地服务器、落地服务器到目标网站。直连和中转的分歧,全部集中在中间那一段——跨境的部分是自己硬闯公网国际出口,还是先交给一台位置更好的机器代为转发。

这个区别之所以在晚上才暴露,是因为拥堵有明确的发生地点和时间。理解了路段,就能解释为什么"多绕一跳反而更快"这种反直觉的事情天天发生。

## 直连和中转的数据包分别走了哪几段路

| 路段                | 直连节点       | 中转节点                   | 这一段的主要风险         |
| ------------------- | -------------- | -------------------------- | ------------------------ |
| 第一段:设备到接入   | 家宽直接出网   | 连到境内/边缘入口机        | 本地运营商绕路           |
| 第二段:跨境         | 走公网国际出口 | 走入口机采购的专用跨境路径 | 晚高峰排队、丢包         |
| 第三段:入口到落地   | 无此段         | 入口机转发到境外落地       | 转发机本身的带宽与负载   |
| 第四段:落地到目标站 | 境外本地访问   | 境外本地访问               | 落地机负载、出口 IP 信誉 |

直连少一段,结构更简单,故障点也更少。代价是它把全部跨境压力压在第二段——那一段恰好是全国用户在同一时间段共同争抢的资源。

中转把跨境这件事外包给了一台位置更好的机器。多出来的第三段是新增成本,也是新增故障点,但它换来的是第二段不再走那条拥堵的公共通道。

## 为什么多绕一跳的中转反而延迟更低

因为延迟由两部分组成:物理传播时间和排队时间。跳数只影响前者,而且影响很小——多一次转发通常只增加几毫秒。排队时间则不同,一条满负荷的链路可以在单段上堆出上百毫秒的等待。

打个比方:高速堵死的时候,多绕两个路口走一条空的辅路,总时间反而短。中转干的就是这件事。所以判断线路好坏,看跳数是没有意义的,要看每一跳的排队情况。

> 这也是一个常见误判的来源:有人用路由跟踪工具看到中转节点跳数更多,就认为线路更差。跳数多而各段都不排队的路径,体验会明显好过跳数少但有一段堵死的路径。

## 晚高峰的卡顿具体发生在哪一段

几乎总是第二段。判据是延迟劣化的形状:

| 观察到的现象                      | 大概率的问题路段 | 说明                                 |
| --------------------------------- | ---------------- | ------------------------------------ |
| 白天正常,20:00 后延迟翻数倍并丢包 | 第二段跨境       | 国际出口拥堵的典型形态               |
| 全天延迟稳定,速度忽高忽低         | 第四段落地       | 落地机在线人数波动                   |
| 延迟基线整体偏高但平稳            | 第一段或路径绕行 | 本地运营商把流量绕了远路             |
| 只有某几个网站慢,其他都正常       | 第四段之后       | 落地到目标站的路径或出口 IP 判定问题 |

用连续路由跟踪可以把这件事看得更清楚。在白天和晚高峰各跑一次,对比每一跳的延迟增量,拥堵段会明显凸出来:

```bash
# 结构示例,地址为占位符,请替换为你自己的节点地址
mtr -r -c 100 example.invalid          # Linux / macOS,输出各跳丢包与延迟
tracert example.invalid                # Windows,先看整体路径形状
```

看的时候只关注一件事:哪一跳开始延迟出现阶跃式上涨,并且后面所有跳都跟着涨。那一跳就是瓶颈的入口。中间某一跳丢包高但后面几跳正常,通常是那台设备限制了对自身的响应,不代表真的丢包。

## 入口在哪、落地在哪,普通用户怎么看出来

不用工具也有两个可用的线索。

一是延迟数值与物理距离的关系。到香港的往返延迟有物理下限,如果你测到的数值明显低于本地宽带到香港的常见水平,说明你实际连的是一台离你很近的入口机,真正的跨境发生在它之后——这就是中转。

二是延迟的稳定性。直连的延迟随国际出口负载起伏,方差大;中转由入口机接住第一跳,数值通常更平。连续 ping 五分钟看数值抖动范围,比看单次数字信息量大得多。

落地在哪则要看出口:访问一个显示当前 IP 归属的页面,看到的是落地服务器的位置,而不是入口的位置。这一层的判定逻辑,[原生 IP 与广播 IP 的区别](/protocols/how-to-choose/native-ip-vs-broadcast-ip/)那篇有完整解释。

## 直连节点更便宜的成本原因是什么

成本结构决定价格,直连的便宜是结构性的:

| 成本项            | 直连                      | 中转                      |
| ----------------- | ------------------------- | ------------------------- |
| 境内/边缘入口机器 | 不需要                    | 需要,且要按带宽持续付费   |
| 跨境路径采购      | 用公共国际出口,不额外付费 | 需采购优质跨境带宽,单价高 |
| 运维复杂度        | 单台机器                  | 入口与落地都要维护和监控  |
| 流量倍率体现      | 通常 1x 或更低            | 通常高于 1x               |

所以同一个机场里,直连节点常被标成低倍率甚至 0.5x,中转和专线节点倍率更高。倍率不是随便定的,它反映的是机场为这条路径付出的成本差。节点名里这些标记怎么读,可以对照[节点名称速查表](/protocols/how-to-choose/line-name-decoder/)。

## 什么用途适合直连,什么用途必须上中转

| 使用场景                       | 直连够用吗 | 原因                        |
| ------------------------------ | ---------- | --------------------------- |
| 白天查资料、收发邮件           | 够用       | 对延迟和持续吞吐都不敏感    |
| 非高峰时段大文件下载           | 够用       | 避开了拥堵时段,带宽成本更低 |
| 晚高峰看高码率视频             | 通常不够   | 持续吞吐撑不住,缓冲频繁     |
| 语音、视频会议                 | 不够       | 对抖动和丢包极敏感          |
| 长时间运行的 AI 对话或流式输出 | 不够       | 连接一断就要重来            |
| 游戏                           | 不够       | 延迟抖动直接体现为操作延迟  |

一个务实的配置是两者混用:日常和下载走低倍率直连省流量,晚高峰和实时任务切到中转。大多数客户端都支持按规则分流,不必手动来回切。

## 从节点名和延迟曲线怎么初步判断类型

按这个顺序看,三分钟能得出初判:

1. 先看节点名有没有线路标记(如 BGP、专线缩写、中转字样)和倍率,倍率高于 1x 的基本不是普通直连;
2. 连续 ping 三分钟,记下延迟的最低值、最高值和波动范围;
3. 晚上 21 点前后再测一次同一节点,对比与白天的差值;
4. 白天晚上都平稳、且延迟低于该地区物理下限的,判为中转;落差大且晚上伴随丢包的,判为直连。

> 节点名里的线路标记是机场自行填写的文本,没有任何认证机制。它可以当筛选线索,不能当结论。涉及付费决策时,用上面这套时段对比自己核一遍更可靠,详细方法见[怎么判断线路是否真实](/protocols/how-to-choose/verify-line-and-ip/)。

## 小结

直连和中转的差别不在机房,而在跨境那一段走公网还是走采购来的路径。晚高峰的劣化几乎全部发生在公网国际出口上,这解释了为什么多一跳的中转反而更快——跳数只加几毫秒,排队能加几百毫秒。判断节点类型不用工具也能做:看延迟是否低于物理下限,以及白天与晚高峰的落差有多大。直连便宜是因为省掉了入口机和跨境带宽采购,把它用在白天和下载上完全合理,别用在实时任务上。
