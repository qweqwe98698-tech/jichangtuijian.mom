「Netflix 解锁」这个说法把一件三段式的事压成了一个开关，围绕它的误解也大多来自这里。真实顺序是：平台先按出口 IP 判断你属于哪个国家的服务区，再在这个服务区的目录里按条目版权决定你能看到什么，最后由风控模块决定要不要弹出那句代理提示。三段各自独立运行，任何一段的结果都推不出另外两段。

被误读得最厉害的是「只能看自制剧」。这个现象恰恰说明前两段都通了——地区判定成功、片库确实切过去了，只是片库里由第三方持有版权的条目对当前出口不开放。它和「打开直接红屏」属于两种完全不同的状态，处理动作也不该一样。

拆成三段还有个很实际的好处：你会清楚换节点这个动作到底能改变什么。它只作用在第一段和第三段，第二段是版权合同，换多少个节点都动不了。

## 三层机制分别在管什么

三层的判定依据、可观察现象和可干预程度差别很大，先把它们放进一张表：

| 层级     | 判定依据                 | 你看到的现象                       | 换节点是否有用                     |
| -------- | ------------------------ | ---------------------------------- | ---------------------------------- |
| 地区片库 | 出口 IP 的归属国家       | 界面语言、推荐位、分类整体换了一版 | 有用，这是节点唯一能直接决定的一层 |
| 条目版权 | 该内容在此地区是否获授权 | 搜不到某部剧，或详情页显示不可用   | 无用，同地区任何节点结果一致       |
| 代理检测 | IP 段的使用特征与信誉    | 弹代理提示，或播放键点下去一直转圈 | 有用，但取决于新 IP 是否也被标记过 |

第一层是可以「切」的，第二层是合同规定的，第三层是概率性的。先把一次失败归到某一层，后面的动作才不至于瞎试。

第一层用到的归属地库、ASN 与 DNS 出口如何共同参与判定，[IP 地区判定原理的五层拆解](/unlock/region-lock/how-platforms-detect-region/)讲得更细，这里只谈它在 Netflix 上的具体表现。

## 为什么自制剧几乎总能播

自制内容——平台自己出品，或者买断了全球发行权的那一部分——版权归属很简单：全球一份，不分地区授权。只要判定落到了任意一个服务区，这类内容就在目录里。

第三方版权剧完全是另一回事。同一部剧在不同国家可能由不同发行方持有，甚至在某些国家根本没上架过。平台必须按地区逐条控制可见性，否则就是违约。所以「换了美国节点却搜不到某部剧」很多时候不是节点的问题，是这部剧在美区就没有。

> 用自制剧验证解锁会得到偏乐观的结论，用热门第三方剧验证会得到偏悲观的结论。想测准，应该挑一部**只在目标地区上架**的内容作为验证对象。

## 那句代理提示到底在检测什么

弹窗的措辞暗示平台「看穿了你在用代理」，但检测手段并不神秘，也不针对协议。它主要看 IP 侧的几类信号：

- **ASN 类型**：这段 IP 登记在数据中心名下，还是民用宽带运营商名下。
- **并发密度**：同一个 IP 上同时活跃着多少个互不相干的账号。
- **地理跳变**：同一个账号在短时间内于相距很远的地区之间来回切换。
- **历史标记**：这段 IP 过去是否已经被批量标记过。

四项都与你用什么协议、开不开 TUN 无关。换协议、换端口对它没有影响，只有落到一段尚未被标记的 IP 上才可能改变结果。而干净 IP 是会被持续消耗的资源，消耗与轮换的具体机制在[流媒体节点为什么这么容易失效](/unlock/region-lock/streaming-node-failure/)里有完整解释。

## 同一个地区，为什么不同节点看到的片库不一样

标着同一个国家的两个节点给出不同结果，通常来自三个原因。

第一是归属地库不一致。IP 的登记信息和第三方数据库的记录可能有出入，平台采信哪一份，决定了你落在哪个服务区，这一点在广播 IP 上尤其明显。

第二是被标记状态不同。一个节点已经进了名单、另一个还没有，表现出来是一个能播一个转圈，而两者的地区判定其实都成功了。

第三是子区域差异。少数地区会因运营商或城市不同出现细微的目录差别，这种情况不算常见，但足以让两次测试对不上。

要区分是哪一种，得先记录两次的出口 IP 国家、城市与 ASN 再做比对。原生 IP 与广播 IP 在这件事上的实际差距，[原生 IP 解锁的真实作用](/unlock/region-lock/native-ip-unlock-truth/)有专门讨论。

## 网页端和 App 端为什么会不同步

同一台设备上浏览器能看、App 不能看，几乎从来不是 Netflix 的判定出了岔子，而是两条路径的实际出口不是同一个。App 可能用自带的解析逻辑绕过了系统代理，也可能在移动网络下悄悄走了 IPv6 直连。

还有缓存因素：切换出口之后，App 不一定立刻重新拉取地区信息，会在一段时间内继续沿用上次的服务区。退出账号重新登录，或者清掉 App 数据，一般能强制刷新。

这类跨端不一致有自己独立的成因链条，[同一节点电脑能看手机不能看](/unlock/region-lock/device-gap-same-node/)把它拆成了系统代理接管范围、App 自带 DNS、蜂窝网络与 IPv6 四项。

## 4K 播放失败其实是另一件事

清晰度上不去经常被记在「解锁失败」头上，但它和地区判定不在一条链路上，卡点在另外三处：账号套餐档位是否包含最高清晰度、播放设备与浏览器是否支持所需的数字版权管理方案、以及链路的持续带宽够不够。

按常见码率推算，4K 串流对持续带宽的要求通常在每秒十几兆比特这个量级，而且要求全程稳定而非峰值达标（具体数值随内容编码差异很大，此处仅作参考）。共享节点在晚高峰掉到这个门槛以下是很正常的事，表现出来就是自动降档或者反复缓冲。

> 排查清晰度问题时，请先在不开代理的本地网络里测试同一部内容。本地也上不去最高档，说明问题在账号或设备，与节点无关。

## 用最少的步骤判断是片库问题还是节点问题

按下面的顺序走，几分钟内基本能定位。

1. **先查出口 IP 的国家与 ASN**。这是所有判断的坐标系，不知道自己被判定到了哪里，后面的现象都没法解释。
2. **看界面是否已经换版**。语言、推荐位、分类整体变了，说明第一层通过；界面完全没变，问题出在节点或分流规则，不必往下测。
3. **搜一部只在目标地区上架的内容**。搜得到说明片库正确；搜不到但界面已换版，那就是第二层的版权限制，换节点无效。
4. **点播放并等待起播**。能起播说明三层都通过；转圈或弹代理提示，卡点在第三层，需要换一段 IP。

第一步的查询可以直接在终端里完成：


四步的结果组合起来只有几种可能，对照下表就能得到结论：

| 界面已换版 | 搜得到目标内容 | 能起播 | 结论与下一步                                 |
| ---------- | -------------- | ------ | -------------------------------------------- |
| 否         | —              | —      | 出口没真正走出去，检查节点与分流规则         |
| 是         | 否             | —      | 该内容在此地区无授权，应该换地区而不是换节点 |
| 是         | 是             | 否     | IP 已被标记，需要换到另一段 IP               |
| 是         | 是             | 是     | 三层均通过，剩下的问题属于带宽或账号         |

## 小结

Netflix 的结果由三层共同决定：出口 IP 决定服务区，版权决定这个服务区里有什么，风控决定放不放行。「只能看自制剧」说明前两层都通了，缺的是版权而不是节点，换节点解决不了。弹代理提示才是真正落在节点上的问题，而且只有换到未被标记的 IP 段才有效。跨端结果不一致先怀疑两端出口不同，清晰度上不去则基本属于账号、设备与带宽的范畴。判断顺序永远是先定位在第几层，再决定动哪个变量。
